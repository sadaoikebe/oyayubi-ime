# 防御コードの棚卸しと、致命的な挙動の監査（2026-11-13）

対象: ブランチ `docs-and-eval-2026-11-10` の `321861e`（v0.1.0 として配布したもの）。
この文書は調査結果と解決案だけを書く。**コードはまだ何も直していない。**

## 0. 結論

1. 起動ループは「1 か所のバグ」ではなかった。**「サーバーが起動に失敗する」原因が何であっても、
   同じウィンドウの嵐になる構造**になっている。起動に失敗する原因は、読んだだけで 8 通り見つかった（§2 A-2）。
   今回はたまたまアンインストールが引き金だっただけで、設定ファイルの書き損じ 1 文字でも同じことが起きる。
2. 同じ構造の再発経路がもう 1 本ある。**更新（setup.ps1 の再実行）**である。IME を使っている最中に更新すると、
   止めたサーバーを TIP が 1 秒で起動し直し、書き換え中のファイルの上で動かす（§2 A-5）。
   Sadao さんの PC では更新を試す前に事故が起きたので、まだ踏んでいないだけ。
3. 「防御」の多くは、失敗を**隠す**方向に働いている。握りつぶし・黙って別経路に切り替え・
   成否を確かめずに「OK」と表示、が合計 20 か所以上ある（§3、A-14）。そのため、壊れたときに
   何が起きているのか利用者にも開発者にも見えない。今回、原因の特定に時間がかかったのもこのせい。
4. 逆に、**本当に必要な防御が抜けている**箇所がある（学習履歴が際限なく増えて毎回全部読み直す、
   使用中のファイルを消す前に確かめない、登録の成否を見ていない、など。§4）。
5. 変換の中核（`session.py`、打鍵 FSM、ビタビ、文節）には握りつぶしが 1 つも無く、問題は見つからなかった。
   問題は **TIP のプロセス管理・サーバーの起動経路・インストーラ**に集中している。

直し方の方針は「防御を足す」ではなく **「危険な動作そのものを無くす」**。
TIP が自分からプロセスを起動しなければ、起動ループは作りようがない（§5）。

## 1. 判定の物差し

防御コードごとに次の 3 つを問うた。

- **その失敗は普通の使い方で起きるか。** 起きないなら防御は要らない（落ちて原因が見える方がよい）。
- **防御が働いたとき、利用者に何が起きるか。** 「黙って別の動きをする」「黙って繰り返す」は不可。
- **防御が働いたことが、あとで分かるか。** 分からないなら、それは防御ではなく隠蔽。

そして絶対に守る条件（不変条件）を 5 つ置く。§2 はこれを破っている箇所の一覧である。

- **I-1** TIP（他人のアプリの中で動く DLL）は、利用者の操作なしにプロセスを起動しない。
- **I-2** どの失敗も、自動で繰り返さない。失敗したら止まって、止まったことを見せる。
- **I-3** ウィンドウは 1 枚も勝手に出さない。
- **I-4** インストール・更新・削除は、途中で失敗しても「前の状態」か「次の状態」のどちらかで終わる。
- **I-5** 成功と表示するのは、成功を確かめたときだけ。

## 2. 致命的な問題（PC を使えなくする／信頼を失う）

### A-1. サーバーの起動ループ【実測】 — I-1, I-2 違反

`oyayubi_tip.cpp:577-620`（`Server::Run`）。接続できなければ `SpawnResident()` で Python を起動し、
15 秒待ち、1 秒休んで、また起動する。回数の上限も、間隔の延長も、あきらめる条件も無い。

しかもこのループは **PC に 1 本ではない**。`Tip` オブジェクト 1 個につき 1 本
（`oyayubi_tip.cpp:1106` の `Server server_` と `1735` の `server_.Start()`）で、`Tip` は
「IME を使ったことのあるスレッド」ごとに作られる。エクスプローラ、ブラウザ、エディタ…と
開いているアプリの数だけループが並走する。サーバーが起動できない状態では、それぞれが 16 秒ごとに
Python を起動し続ける。アプリが 10 個なら 1.6 秒に 1 回。

さらに、**IME の登録を解除しても止まらない**。DLL を読み込み済みのプロセスは、そのプロセスが
終わるまで動き続ける（今回 `explorer.exe` と VS Code がそうだった）。

### A-2. 「サーバーが起動に失敗する」原因はいくらでもある【コード上確実】

A-1 のループは、サーバーが立ち上がりさえすれば止まる。問題は、立ち上がらない原因が多いこと。
以下はどれも、起動時に例外で落ちる（＝ループに入る）。

| # | 原因 | 場所 |
|---|---|---|
| 1 | `config.json` が JSON として壊れている（手で編集して `,` を 1 つ落とす、など） | `config.py` `read_config` — 「不明なキーは無視」はあるのに、構文エラーは素通しで落ちる |
| 2 | `config.json` の値の型が違う（数値の欄に文字） | 同上 `action.type(value)` |
| 3 | 辞書キャッシュ（pickle）が途中までしか書けていない | `mozc_dict.py:153-162` — 直接上書きしているので、書いている最中に止められると壊れたファイルが残る。次回から `pickle.loads` が毎回落ちる |
| 4 | 辞書ファイルが足りない | `require_dict_files`（これ自体は正しい。問題は落ちたあと） |
| 5 | venv の元になったシステムの Python を、あとで利用者が消した／上げた | venv 経路。`runtime\Scripts\python.exe` が動かなくなる |
| 6 | アンインストールや更新でファイルが半分だけある | 今回の事故 |
| 7 | 個人辞書 `user_lexicon.jsonl` の 1 行が壊れている | `mozc_dict.py` `apply_user_lex` — `json.loads` と `row["reading"]` がむき出し |
| 8 | Python 本体や torch を、ウイルス対策ソフトが隔離した | — |

1 の仲間に、リリース直前に CI で実際に踏んだ「`config.json` に BOM が付いていて読めない」がある（修正済み）。
CI では「テストが落ちた」で済んだが、利用者の PC で起きていれば今回と同じウィンドウの嵐になっていた。

加えて、サーバーの標準エラー出力は捨てられている（`oyayubi_tip.cpp:546-553`、NUL に接続）。
**落ちた理由はどこにも残らない。** 利用者から見えるのは「ウィンドウが出続ける」だけ。

### A-3. コンソールウィンドウが出る【実測】 — I-3 違反

`oyayubi_tip.cpp:565-567`。`DETACHED_PROCESS`（コンソール無し）で起動しているが、venv の
`Scripts\python.exe` は本物の Python を**子プロセスとして起動し直すだけの小さなランチャー**で、
その子には指定が引き継がれない。コンソールを持たない親から生まれたコンソールアプリには、
Windows が新しいコンソールを作る。それが Windows Terminal として見えた（記録:
`python.exe (16812) <- explorer.exe` → `python.exe (24136) <- python.exe (16812)` → `conhost` →
`WindowsTerminal.exe`）。

同梱ランタイム経路ではランチャーを挟まないので出ない。つまり **「2 つあるインストール経路の片方だけで
起きる不具合」**で、CI は両方の経路でインストールまでは試したが、どちらも IME を選んで打鍵することは
していなかったので見つからなかった。

### A-4. アンインストールが、動いている最中のファイルを消す【実測】 — I-4 違反

`uninstall.ps1:95-107`。登録解除 → サーバー停止 → フォルダ削除、の順に進むが、DLL を読み込んだ
アプリが残っている限り DLL は消せない。`Remove-Item -Recurse` は**消せるものから順に消して、
消せないものを残す**。結果、「DLL は生きている・Python のソースは半分無い」という状態になり、
生きている DLL が A-1 のループで壊れたサーバーを起動し続けた。

設計書 `docs/INSTALL.md:105` には「中途半端に消さない」と書いてある。**実装が設計と違う。**

### A-5. 更新が、動いている最中のファイルを書き換える【コード上確実・未実行】 — I-4 違反

`setup.ps1:213-230`。更新のとき、

1. 常駐サーバーを止める（`Stop-Process`）。
2. ソース zip を `app\` に上書き展開する。
3. DLL を上書きする。**使用中なら失敗して中止**（「アプリを全部閉じてください」）。

IME を使っている PC では、次のことが起きる。

- 1 の直後、TIP が 1 秒以内にサーバーを起動し直す（A-1）。そのサーバーは 2 以降で書き換え中のファイルを読み、
  `pip` が入れ替えようとしている torch の DLL をつかみ、`setup.ps1:283` が消そうとする辞書キャッシュを
  同時に作り直す（A-2 の 3 の原因になる）。
- 3 は**ほぼ必ず失敗する**。エクスプローラが DLL を読み込んでいるからで、「アプリを全部閉じる」では外れない。
  サインアウトすれば外れるが、サインアウトしたら setup は実行できない。
- 3 で中止した時点で、2 は済んでいる。**「Python 側は新版・DLL は旧版」**が残る。

新旧の組み合わせで通信の形式が少しでも違うと、TIP は接続を拒否する（A-6）。拒否した TIP は
「サーバーがいない」と判断してサーバーを起動する。サーバーは既にいるので新しい方はすぐ終わる。
これが 16 秒ごと、アプリの数だけ、永久に続く。**今回と同じ嵐が、更新でも起きる。**

### A-6. 自分のサーバーの返事を疑いすぎて、接続を切る【コード上確実】

`oyayubi_tip.cpp:483-488`。接続時の挨拶の返事を `hello.object.size() != 3`（項目がちょうど 3 個）で
検査している。サーバー側が項目を 1 つ足しただけで、古い DLL は接続できなくなる。
`ParseReply`（`276-312`）も、毎回の返事の全項目の存在と型を検査し、1 つでも合わなければ接続を切る。

相手は自分で書いたサーバーで、しかもトークンで本人確認済み。ここまで疑う相手ではない。
そして「疑って切る」→「いないと判断して起動する」が A-1 につながるので、**害しかない検査**になっている。

### A-7. Python が見つからないとき、別の Python を探して起動する【コード上確実】

`oyayubi_tip.cpp:233-246, 504-516`。インストール先の `runtime\` に Python が無いと、

1. `PATH` 上の `python.exe` を探す。Python を入れていない Windows では、これは
   **Microsoft Store を開くためのスタブ**（`WindowsApps\python.exe`）に当たる。
2. 無ければ 開発者個人の `C:\Users\<名前>\AppData\Local\Programs\Python\Python313\python.exe`。
   **開発機の個人のパスがそのまま出荷物に入っている。**
3. 無ければ `C:\Windows\py.exe`。

「インストール先の Python が無い」は、アンインストール途中か壊れたインストールでしか起きない。
そのときに取るべき動作は「何もしない」であって、「別の Python で、無いはずのモジュールを実行する」ではない。
1 に当たると、A-1 のループが Store のウィンドウを開き続ける可能性がある【要確認】。

### A-8. サーバーが、たまたま最初に打鍵したアプリの子になる【コード上確実／影響は要確認】

サーバーは「最初に IME を使ったアプリ」から起動され、そのアプリの環境をそのまま引き継ぐ。

- **環境変数**: `PYTHONPATH` や `PYTHONHOME` を設定しているアプリ（開発ツールの中の端末など）から
  起動されると、別のライブラリを読み込む。
- **権限**: 管理者として実行中のアプリから起動されると、サーバーも管理者権限で動く。
- **ジョブ**: 「閉じたら子プロセスも全部終了」という設定で動いているアプリから起動されると、
  そのアプリを閉じたときサーバーも道連れになる（→ 別のアプリの TIP が起動し直す → A-3 のウィンドウ）。
- **サンドボックス**【要確認】: `GUID_TFCAT_TIPCAP_IMMERSIVESUPPORT`（`oyayubi_tip.cpp:59`）を名乗っているので、
  スタートメニューの検索欄や「設定」など、サンドボックスの中のアプリにも読み込まれる。
  そこからはローカル接続が原則できず、起動した Python もサンドボックスの中で動くので辞書を読めない。
  つまりそこでは IME は働かず、A-1 のループだけが回る、と推定される。

### A-9. 学習履歴が増え続け、確定のたびに全部読み直す【実測: 1 万行 46ms／10 万行 368ms】

`learning.py`。確定のたびに `learning.jsonl` に 1 行足し（`_append`）、直後に `sync()` を呼ぶ（260 行）。
`sync()` はファイルが変わっていれば**全体を読み直して全行を解析し直す**（96-161 行）。自分で 1 行足したので、
必ず変わっている。

ファイルは追記だけで、古い行を整理する処理は無い。毎日使えば数か月で数万〜十万行になり、
1 回の確定ごとにかかる時間が行数に比例して延びていく。TIP は 250 ミリ秒で返事が無ければ接続を切る（A-10）。
**使い込むほど遅くなり、ある日から入力中の文字が消え始める**、という時限式の不具合。

### A-10. 250 ミリ秒遅れただけで、入力中の文字を捨てる【コード上確実】

`oyayubi_tip.cpp:1392-1400`（`ExchangeReply`）。返事が 250 ミリ秒以内に来なければ接続を切り、
`ClearLocal()` で**変換中の文字列を画面から消す**。その打鍵はアプリに素通しされるので、
かな入力の途中にローマ字が 1 文字混ざる。

サーバーは生きていて、ただ 1 回遅かっただけ（ディスクが混んだ、他の重い処理が走った、A-9）でもこうなる。
続いて TIP は再接続し、再接続の挨拶も 250 ミリ秒を超えると「いない」と判断して起動に進む（A-1）。

同じ場所に関連がもう 1 つ。`oyayubi_tip.cpp:1244-1247` は、**アプリ側が編集を断っただけ**でも
サーバーとの接続を切る（`edit rejected`）。断ったのはアプリで、サーバーに落ち度は無い。

入力途中の長さにも上限が無く、打鍵のたびに入力全体を解析し直す（`session.py` `_refresh`）。
実測では 200 字で 38ms、400 字で 98ms と長さに比例する。それより深刻なのは**起動後の最初の 1 回が 617ms**
かかることで、サーバー起動直後の最初の打鍵は必ず 250 ミリ秒を超える。

解決の全体設計は `docs/REDESIGN.md` にまとめた。

### A-11. 異常を握りつぶして、壊れたまま動き続ける【コード上確実】

`oyayubi_tip.cpp:1024-1032, 1444-1447, 1509-1518, 1527-1538`。打鍵・編集・タイマーの処理全体を
`__try / __except(EXCEPTION_EXECUTE_HANDLER)` で囲み、メモリ違反を含むあらゆる異常を捕まえて続行している。

- 異常が起きた時点でロックを持っていれば、ロックは二度と解放されない。以後 `Send` は必ず失敗し、
  そのアプリの中で IME は**黙って死んだまま**になる。
- C++ の後始末（デストラクタ）を走らせる指定（`/EHa`）がビルドに無いので、確保したものは漏れる。
- 何より、バグがあっても落ちないので**バグがあることに気づけない**。

「IME が落ちるとアプリを道連れにする」のは事実で、動機は分かる。しかし答えは握りつぶしではなく、
落ちる原因を無くすこと。

### A-12. 全アプリの中で、秒間 60 回のタイマーが回り続ける【コード上確実】

`oyayubi_tip.cpp:1158`（`SetTimer(…, 16, …)`）。IME を使っていなくても、直接入力モードでも、
アプリごと・スレッドごとに 16 ミリ秒周期で `OnTimerImpl` が走り、毎回フォーカスの問い合わせをする。
候補を表示している間は、毎回アプリに読み取りを要求する（`1433`）。

必要なのは「親指キーの同時打鍵の判定期限が来た」ときだけなので、期限のあるときに 1 回だけ
タイマーを掛ければ足りる。常時ポーリングは、ノート PC の電池とアプリの応答性を削る。

同じ種類の無駄として、**1 回の打鍵につき 4 回以上**、パスワード欄かどうかをアプリに同期問い合わせ
している（`Eligible()` → `KeyboardDisabled()` → `PasswordScope()`、`795-802`）。
問い合わせを断るアプリでは「パスワード欄」と見なして黙って素通しにするので、
**IME が効かないアプリが、理由の分からないまま生まれる**。

### A-13. 管理者権限のプロセスに、誰でも書き換えられる DLL を読み込ませている【コード上確実】

DLL は `%LOCALAPPDATA%\oyayubi-ime\app\NicolaIME3.dll`（一般ユーザーが自由に書き換えられる場所）にあり、
それを `HKLM`（PC 全体）に登録している（`register_admin.py`）。IME は管理者として実行中のアプリにも
読み込まれるので、**一般権限のプログラムがこの DLL を差し替えれば、管理者権限を奪える**。
登録・解除で、同じく書き換え可能な場所の `python.exe` を管理者権限で実行しているのも同じ問題。

悪意のあるプログラムが既に PC に入っていなければ実害は無いが、「出荷品質」と言うなら直す必要がある。
IME の DLL は `Program Files` に置くのが通例。

### A-15. アンインストールが、学習データを確認なしで消す【コード上確実】

学習履歴と個人辞書は、プログラムと同じフォルダ（`app\data\`）にある。アンインストールは既定で全部消す。
残すには `-KeepData` を付ける必要があり、付け忘れたら戻せない。
一般の IME は、アンインストールしてもユーザー辞書は残す。置き場所を分けていないのが根本。

### A-16. 初回インストールが途中で失敗すると、やり直せない【コード上確実】 — I-4 違反

`setup.ps1:139-141`。インストール記録が無いのに `app\` に中身があると「未知の内容があります。
上書きしません」で中止する。ところがインストール記録は**最後に**書く（`344`）。
途中（たとえば 500MB のモデル取得中の回線切れ）で失敗すると、次からは毎回この中止に当たる。
利用者は自分でフォルダを消すしかない。「他人のファイルを上書きしない」ための防御が、
自分の失敗の後始末を妨げている。

## 5. 解決案

防御を足すのではなく、**危険な動作ができない構造にする**。

### 5.1 サーバーの起動は 1 か所だけ。TIP は起動しない

- **起動するのは、サインイン時（スタートアップ登録 1 件）と、利用者がメニューで「変換サーバーを起動」を
  選んだときだけ。** ウィンドウの出ない `pythonw.exe` で起動する。
- TIP は**接続するだけ**。接続していないときに打鍵があったら、裏で 1 回だけ接続を試す
  （ファイルを 1 つ読んで、自分の PC の中のポートにつなぐだけ。プロセスは起動しない）。
- サーバーが落ちたら、キーは素通しになり、タスクバーの表示が変わる（D-2）。それ以上は何も起きない。
- 設定を変えたときの再起動は、管理ウィンドウが自分で「止めて、起動する」。
  いまは「止めれば TIP が起動し直してくれる」ことに頼っている（`manage.py` `restart_server`）ので、ここも直す。

これで I-1・I-2・I-3 は「守る」のではなく**破りようがなくなる**。A-1・A-3・A-7・A-8 と、
A-2・A-5・A-6 の「嵐になる」部分が消える。`SpawnResident`・代替 Python 探索・毎秒の死活確認・
ハンドル引き継ぎの制限が、TIP から丸ごと無くなる。

（別案: サインイン時の登録を避け、TIP が「サインインにつき 1 回だけ」起動する。
PC に常駐の登録を増やさずに済むが、A-8 の問題が全部残るので採らない。）

### 5.2 Python の経路は同梱ランタイム 1 本

venv 経路・システム Python の探索・`-EmbeddedPython` スイッチ・CI の 2 経路を削る。
利用者の PC にどんな Python があっても無くても、同じものが同じ場所に入る。

### 5.3 削除と更新は「名前を変えてから」

Windows では、**読み込まれている DLL は消せないが、名前は変えられる**（開発用の `dev-build.ps1` が
A/B の 2 スロットでやっているのと同じ理屈）。

- **アンインストール**: ①登録解除し、解除できたことを確かめる。②サーバーを止める（5.1 により、もう誰も
  起動し直さない）。③DLL 以外を消す。④DLL は消せなければ名前を変えて残し、「次にサインインしたとき
  消えます」と表示して正常終了する（サインイン時に 1 回だけ動く削除を登録）。
  **再起動やサインアウトを強制しない。途中で止まらない。**
- **更新**: ①サーバーを止める。②新版を**別フォルダ**に全部用意する（取得・展開・辞書・検証まで）。
  ③用意できたら、古い DLL の名前を変え、フォルダを入れ替え、登録し直す。④サーバーを起動する。
  ②のどこで失敗しても、旧版は手つかずで動き続ける。
- **学習履歴・個人辞書・設定は `~/.oyayubi-ime\` に置く**（プログラムのフォルダから出す）。
  更新では触らない。アンインストールでは既定で**残し**、`-RemoveData` を付けたときだけ消す（A-15 の逆）。
- DLL の置き場所は `Program Files` にする（A-13）。登録・解除は PowerShell から直接行い、
  Python を管理者権限で動かさない。

### 5.4 TIP の単純化

- 返事は使う項目だけ読む。知らない項目は無視、無い項目は既定値（A-6）。
- 250ms で返事が無いとき: その打鍵は素通しにするが、**接続は切らず、変換中の文字も消さない**。
  遅れて届いた返事は捨てる（要求に通し番号を付ければ見分けられる）。続けて何度も遅れたときだけ切る（A-10）。
- アプリが編集を断っても、サーバー接続は切らない。
- 握りつぶし（`__try`）を外す（A-11）。
- タイマーは期限があるときだけ（A-12）。パスワード欄の確認はフォーカス移動時に 1 回。
- 調査用ログと代替経路を削る（§3.1）。

### 5.5 見えるようにする

D-1（サーバーのログ）、D-2（タスクバーの表示）、D-6（登録の成否）。
LM が無効になった・学習が止まった、も管理ウィンドウの「状態」に出す。

### 5.6 順番

1. 5.1 と 5.2（嵐の根を断つ）。
2. 5.3（削除と更新）。
3. D-1・D-2・A-14（見えるようにする、嘘を言わない）。
4. A-9・D-3（学習履歴とキャッシュ）。
5. 5.4 の残りと §3 の削除。
6. A-13（置き場所）は 5.3 と同時にやるのが楽だが、分けてもよい。

## 6. 確かめ方

今回の一番の反省は、**「インストールできた」ことしか試験していなかった**こと。CI は setup が終了コード 0 で
終わることを見ていただけで、IME を選んで 1 文字も打っていない。次は Sadao さんの PC に入れる前に、
捨ててよい Windows（Windows サンドボックスか仮想マシン）で、下を全部通す。

不変条件を、機械で数えられる形にする。

- **プロセス数**: 下の各操作の前後 60 秒で、新しく生まれたプロセスの一覧を記録する
  （今回、原因を突き止めたのと同じ方法）。利用者が起動したもの以外は **0 個**であること。
- **ウィンドウ数**: 同じく、新しく現れたウィンドウが **0 枚**であること。

操作（それぞれ、メモ帳・ブラウザ・エクスプローラを開き、IME を選んで打鍵した状態から）:

| 3 | メニューから「変換サーバーを起動」 | 戻る |

| 5 | 辞書キャッシュを 0 バイトにして起動 | 同上 |
| 6 | **アプリを開いたまま**更新 | 完了する。学習データが残る。新しく開いたアプリは新版 |
