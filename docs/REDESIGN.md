# yuragi-ime 全体再設計（2026-11-13）

`docs/DEFENSIVE_CODE_AUDIT.md`（監査）で見つかった問題を、個別の修理ではなく構造から直すための設計書。
実装者（Opus）がこの文書だけで作業に入れるように書く。監査の項目番号（A-1 など）はそのまま参照する。

**読み方**: §1〜§3 が考え方、§4〜§8 が部品ごとの仕様、§9 が画面と文言、§10 が作業順と合格条件。
仕様の中の数値は §11 の定数表にまとめてある。「【実装時に確認】」は、Windows の挙動を実機で確かめてから
確定する箇所。

## 2. 考え方

### 2.1 「再起動しない」でも「いくらでも再起動する」でもなく、「監督者が、決まった回数だけ」

前回の事故の本質は「再起動したこと」ではなく、次の 3 つが重なったこと。

1. 再起動を決める者が**アプリの数だけいた**（TIP ごとに 1 本のループ）。
2. 回数に**上限が無かった**。
3. 再起動のたびに**ウィンドウが出た**。

したがって直し方は、再起動をやめることではない。**再起動を決める者を PC に 1 人だけにし、回数を数え、
見えないところで行う**こと。それが「ブローカー」（§5）である。

### 2.2 壊れやすいものほど内側に、頑丈なものほど外側に

```
アプリ ──[TIP DLL]──(名前付きパイプ)──[ブローカー]──(標準入出力)──[変換エンジン]
          薄い・状態が少ない          小さい・ネイティブ        大きい・Python・1.2GB
          アプリの中で動く            落ちない前提で作る        落ちることを前提に扱う
```

- **TIP** は他人のアプリの中で動く。ここで間違えるとアプリを巻き込む。だから**できることを減らす**:
  打鍵を送る、返事を画面に書く、それだけ。プロセス管理・再試行・ファイル読み書きは持たない。
- **変換エンジン**は大きく、辞書・学習・LM・torch を抱える。落ちる可能性が一番高い。だから
  **落ちても誰も困らない位置**に置く。エンジンと直接話すのはブローカーだけ。
- **ブローカー**はその間に立つ小さな常駐プログラム（C++、数百行）。エンジンを起動し、見張り、
  落ちたら決まった回数だけ起動し直し、その間に届いた打鍵を預かる。TIP から見ると
  「エンジンが落ちた」は「返事が少し遅い」にしか見えない。

いまはこの役目（起動・見張り・再接続）が TIP の中にあり、TIP は試験ができない（TSF の中でしか動かない）。
ブローカーは**ただの exe なので、CI で落とす・固める・殺す試験が書ける**。これが構造を変える一番の理由。

### 2.3 状態を増やさない

頑丈さは、回復の仕組みを足すことではなく、**取りうる状態を数えられるほど少なくする**ことで得る。
この設計で利用者に見える状態は 4 つだけ（§9）。エンジンの起動失敗の原因が 8 通りあっても（A-2）、
利用者に見える結果は「数秒待つと直る」か「1 回知らせて止まる」の 2 つしかない。

採らなかった案:

- *打鍵の記録を取っておき、エンジン復帰後に再生して変換中の状態を完全に復元する。*
  復元はできるが、「再生したらまた同じ所で落ちる」場合の扱いなど状態が増える。代わりに
  **「落ちたら、見えている文字をそのまま確定する」**（P-1 は守れる。失うのは、その 1 回の再変換の機会だけ）。
- *エンジンが動かないとき用に、TIP の中に簡易かな入力を持つ。* 打鍵の判定ロジックが二重になる。
- *セーフモード（設定を無視して起動し直す）。* 設定・個人辞書・学習の各ファイルを「壊れていても起動できる」
  ように読めば不要（§6.2）。

## 4. 全体の構成

### 4.1 プロセス

| 部品 | 実体 | 数 | 誰が起動するか |
|---|---|---|---|
| TIP | `yuragi_tip.dll`（C++） | アプリのスレッドごと | Windows |
| ブローカー | `yuragi-broker.exe`（C++、ウィンドウなし） | サインインごとに 1 | サインイン時（Run キー）。無ければ TIP が条件付きで（§7.3） |
| エンジン | 同梱 Python で `python -m yuragi.engine` | ブローカーごとに 1 | ブローカーだけ |
| 設定ウィンドウ | `pythonw -m yuragi.ime.admin_ui` | 利用者が開いたとき | ブローカー（TIP のメニューから依頼） |

### 4.2 置き場所

```
%ProgramFiles%\yuragi-ime\<tag>\          管理者だけが書ける。全アプリに読み込まれるものはここ（A-13）
    yuragi_tip.dll
    yuragi-broker.exe

%LOCALAPPDATA%\yuragi-ime\                 利用者の権限で動くものだけ。管理者権限では決して実行しない
    versions\<tag>\app\                     Python のソース
    versions\<tag>\engine.json              このタグが使う共有物への道順（下）
    shared\runtime\<id>\                    同梱 Python + torch + 依存。id = 版とハッシュ
    shared\dict\<上流コミット>\             Mozc 辞書
    shared\cache\<辞書マニフェストのハッシュ>.pkl
    shared\model\<リビジョン>\              LM モデル
    staging\                                更新の作業場。成功したら versions へ移す

%USERPROFILE%\.yuragi-ime\                 利用者のデータ。更新でもアンインストールでも触らない
    config.json  tip.json
    learning.jsonl  personal_lexicon.jsonl
    logs\broker.log  logs\engine.log  logs\engine.prev.log

HKLM  CLSID・TIP 登録 → %ProgramFiles%\yuragi-ime\<tag>\yuragi_tip.dll
HKCU\Software\yuragi-ime   Tag = <tag>     「この利用者には、この版が入っている」の唯一の印
HKCU\…\CurrentVersion\Run   yuragi-ime = "…\<tag>\yuragi-broker.exe"
```

要点:

- **版ごとにフォルダを分ける。** 更新は「新しいフォルダを作って、登録を付け替える」だけで、
  読み込まれている DLL には触らない。だからアプリを開いたまま更新できる（P-7）。
- **大きいもの（ランタイム・辞書・モデル）は中身で名前を付けて共有する。** 中身が同じなら更新で取り直さない。
- **学習履歴と個人辞書をプログラムのフォルダから出す**（A-15）。既存の `app\data\learning.jsonl` と
  `personal_lexicon.jsonl` は、初回の更新時に `~\.yuragi-ime\` へ移す。
- **Python の経路は同梱ランタイム 1 本。** venv 経路とシステム Python の探索は削除する。

## 5. ブローカー（新規、`src/broker/`）

### 5.1 役目

1. エンジンを起動し、見張り、決まった回数だけ起動し直す。
2. TIP からの接続を受け、打鍵をエンジンに渡し、返事を返す。
3. エンジンが使えない間、届いた打鍵を預かる。
4. 直らない故障を、利用者に 1 回だけ知らせる（§9.3）。

やらないこと: 変換の中身を理解すること。メッセージは `sid` と `seq` を見て配るだけ。

### 5.2 起動と終了

- サブシステムは WINDOWS（コンソールを持たない）。ウィンドウは通知用の非表示ウィンドウ 1 枚だけ。
- 二重起動は名前付きミューテックス `Local\yuragi-ime-broker` で防ぐ。取れなければ黙って終了コード 0。
- 起動したら `HKCU\Software\yuragi-ime\Tag` を読み、自分のタグと違えば黙って終了（古い版が残っていた場合）。
- `%LOCALAPPDATA%\yuragi-ime\versions\<tag>\engine.json` が無ければ、状態を `not-installed` にして
  パイプだけ開く（同じ PC の別の利用者。知らせない、何も起動しない）。
- 保守中の印（§8.1 のミューテックス `Local\yuragi-ime-maintenance`）が立っていたら、エンジンを起動せず終了する。
- 終了するのは: パイプで `quit` を受けたとき（インストーラ）、サインアウト。

### 5.3 エンジンの起動のしかた

`CreateProcessW` で、次のとおり。**ここが A-3・A-7・A-8 の答え。**

- 実行ファイルは `engine.json` に書いてある絶対パスの `python.exe` だけ。**無ければ起動しない。別の Python は探さない。**
- フラグは `CREATE_NO_WINDOW`。同梱ランタイムの `python.exe` はランチャーを挟まないので、子も孫もコンソールを作らない。
- 環境変数は**引き継がない**。`CreateEnvironmentBlock` で利用者の既定の環境を作り、
  `PYTHONUTF8=1` `PYTHONIOENCODING=utf-8` `PYTHONNOUSERSITE=1` `HF_HUB_OFFLINE=1` を足し、
  `PYTHONPATH` `PYTHONHOME` を消す。
- 標準入力・標準出力は無名パイプ（ブローカーとの通信）。標準エラーは `logs\engine.log`
  （起動のたびに前の分を `engine.prev.log` に回す。1 本の上限 1MB、超えたら先頭を捨てる）。
- 「ブローカーが死んだら子も死ぬ」ジョブ（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`）に入れる。孤児を残さない。
- 作業フォルダは `versions\<tag>\app`。

### 5.4 エンジンの見張り（状態機械）

```
            起動                  ready 受信              60 秒無事
 STOPPED ────────► STARTING ───────────────► READY ─────────────► （失敗回数を 0 に戻す）
                      │  ▲                     │
       ready 前に終了 │  │ 待ってから起動       │ 終了を検知／5 秒無応答で強制終了
                      ▼  │                     ▼
                    BACKOFF ◄──────────────────┘
                      │
                      │ 上限に達した
                      ▼
                    FAILED ──(利用者が「もう一度試す」／次のサインイン)──► STARTING
```

- **終了の検知**はプロセスのハンドルを待つ（ポーリングしない）。
- **無応答の検知**: エンジンに渡した要求の返事が `ENGINE_HANG_MS` 来なければ、エンジンを強制終了して
  「終了」と同じ扱いにする。エンジンは必ず即答する作りなので（LM 待ちは `pending` で即答）、これは故障。
- **起動中の無音**: STARTING の間、エンジンから `ENGINE_START_SILENCE_MS` 何も来なければ同じく強制終了。
  辞書キャッシュの作り直し（数分）の間は、エンジンが 5 秒ごとに `{"progress":"cache"}` を出す。
- **BACKOFF の待ち時間**: 1 回目 0 秒、2 回目 2 秒、3 回目 10 秒。
- **FAILED に入る条件**（どちらか）:
  - `ENGINE_START_WINDOW_MS`（10 分）の間に `ENGINE_MAX_STARTS`（3 回）起動した。
  - **ready に達する前に 2 回続けて終了した。** 起動時の失敗は何度やっても同じなので、すぐ止める。
- FAILED に入ったら、エンジンの終了コードと `logs\engine.log` の最後の `fatal` 行から理由を決め（§6.6）、
  §9.3 の通知を 1 回出す。**以後、自分からは何も起動しない。**

これで「10 分間に最大 3 回、ウィンドウなし」が上限になる（I-2）。A-2 の 8 通りの原因は、
どれも「2 回試して止まり、理由を 1 回知らせる」になる。

### 5.5 TIP との通信（名前付きパイプ）

- 名前: `\\.\pipe\yuragi-ime-<利用者の SID>-<セッション番号>`。バイト単位、1 行 1 JSON（UTF-8、`\n` 区切り）。
- アクセス権: その利用者に読み書き。加えて「すべてのアプリパッケージ」（`S-1-15-2-1`）に読み書き
  ——スタートメニューの検索欄など、サンドボックス内のアプリからも**接続だけは**できるようにする
  【実装時に確認: 整合性レベルのラベルも必要か】。他の利用者・ネットワークからは不可（`PIPE_REJECT_REMOTE_CLIENTS`）。
- TCP・`endpoint.json`・トークン・`server.lock` は廃止する。パイプが在ること自体が「ブローカーがいる」の印になり、
  古いポート番号が残る問題も、250ms の接続待ちも無くなる。

**メッセージ（プロトコル 1）**

TIP → ブローカー:

```json
{"op":"hello","proto":1,"tag":"v0.2.0","bits":64}
{"seq":17,"op":"down","vk":74,"t":123456,"mods":[]}        ← op は現行と同じ（down/up/timeout/reset/set_direct/toggle_direct）
{"op":"retry"}                                              ← 利用者が「もう一度試す」を選んだ
{"op":"open_admin"}                                         ← 設定ウィンドウを開く
{"op":"quit"}                                               ← インストーラだけが使う
```

ブローカー → TIP:

```json
{"proto":1,"state":"ready","warnings":[]}                   ← hello の返事
{"seq":17, …現行の返事の全項目… }                          ← 要求の返事（エンジンの返事に seq を付けたもの）
{"seq":17,"state":"down"}                                   ← 預かり時間切れ／FAILED 中。この打鍵は処理されなかった
{"event":"state","state":"starting"}                        ← 状態が変わった（要求と無関係に届く）
{"event":"reset"}                                           ← エンジンが入れ替わった。変換中のものは失われた
```

`state` は `ready` `starting` `down` `maintenance` `not-installed` `incompatible` の 6 つ。

**互換の規則**（A-6 の答え。更新後も、開いたままのアプリには古い DLL が残るため必須）:

- 受け取る側は、**知らない項目を無視し、無い項目は既定値にする。** 項目の数や余分を検査しない。
- プロトコル 1 の中での変更は「項目を足す」だけ。意味を変える・消すときは `proto` を 2 に上げる。
- ブローカーは、`proto` が自分と違う TIP には `{"state":"incompatible"}` だけを返す。
  TIP はそれを受けたら素通しになり、§9.2 の「このアプリを開き直してください」を出す。
  **この動作はプロトコル 1 の TIP に最初から入れておく。**

### 5.6 預かり（エンジンが使えない間の打鍵）

- 状態が `starting`（起動中・起動し直し中）の間に届いた要求は、接続ごとの列に順番どおり入れる。
- `ready` になったら、接続ごとに新しいセッションを開き、その接続の直前の入力モード（`direct`）を
  `set_direct` で戻してから、列の要求を届いた順にエンジンへ渡す。打鍵の時刻 `t` は TIP が付けたものを
  そのまま使うので、同時打鍵の判定は預かっていた時間の影響を受けない。
- 列の先頭が `HOLD_MS`（8 秒）を超えた、列が `HOLD_MAX`（256 件）を超えた、状態が FAILED になった
  ——のどれかで、列の全要求に `{"seq":n,"state":"down"}` を返して空にする。
- エンジンが入れ替わったとき（落ちて起動し直したとき）は、列を流す前に全接続へ `{"event":"reset"}` を送る。

### 5.7 試験（CI で実行する。§10 の合格条件）

偽のエンジン（Python の小さなスクリプト。引数で「すぐ落ちる」「N 件目で落ちる」「返事をしない」
「ready を出さない」を選べる）と偽の TIP（パイプにつなぐテストプログラム）で:

- すぐ落ちるエンジン → 起動はちょうど 2 回、状態は `down`、その後 10 分相当（時計を差し替え）起動 0 回。
- N 件目で落ちる → 預かった要求が新しいエンジンに順番どおり届く。TIP 側に `reset` が 1 回届く。
- 返事をしない → 5 秒で強制終了、起動し直し。
- 3 回落とす → FAILED。`retry` で 1 回だけ起動する。
- 全試験を通じて、ブローカーとその子孫が作った最上位ウィンドウは 0 枚。
- ブローカーを強制終了 → エンジンも消える（ジョブ）。

## 6. 変換エンジン（Python、既存を改修）

`session.py`・打鍵 FSM・`lattice/`・`bunsetsu.py`・`predict.py` の**変換の中身は変えない**。
変えるのは、入口（通信）・起動時の読み込み・学習履歴の保存・失敗の扱い。

### 6.1 入口: `yuragi/engine.py`（新規。`resident.py` と `client.py` を置き換える）

- 標準入力から 1 行 1 JSON を読み、標準出力に 1 行 1 JSON を書く。それ以外の通信手段は持たない。
- 起動直後に、本物の標準出力を通信専用に確保し、`sys.stdout` は標準エラーに向け直す
  （ライブラリが `print` しても通信に混ざらないように）。
- 標準入力が閉じたら（ブローカーが死んだら）終了する。
- ブローカー → エンジン: `{"op":"open","sid":3}` `{"op":"close","sid":3}` `{"sid":3,"seq":17,"op":"down",…}`
- エンジン → ブローカー: 準備ができたら `{"ready":true,"proto":1,"warnings":[…]}`。以後は要求 1 件に返事 1 件
  `{"sid":3,"seq":17,…}`。
- セッションは `sid` ごとに 1 つ（現行の「接続ごと」と同じ）。要求は 1 本のスレッドで順番に処理する
  （現行も `dispatch_lock` で直列）。LM は現行どおり別スレッド（`lm_async.py`）。
- 既存の標準入出力モード（`server.py` の `main`）は、テストと評価用にそのまま残す。

### 6.2 起動時の読み込み: ファイルごとの方針

原則: **利用者が触れるファイルは、壊れていても起動を止めない。プログラム自身のファイルが壊れていたら、
はっきり止まる。** いまは逆で、設定の書き損じで止まり（A-2）、辞書の欠落は黙って飛ばす（監査 §3.2）。

| ファイル | 壊れていたら | 利用者への知らせ |
|---|---|---|
| `config.json`（構文・型・不明なキー） | 読めた項目だけ使い、他は既定値 | あり（§9.3 の注意） |
| `personal_lexicon.jsonl` の壊れた行 | その行だけ飛ばす | 設定ウィンドウに件数 |
| `learning.jsonl` の壊れた行 | その行だけ飛ばす | 設定ウィンドウに件数 |
| `learning.jsonl` が読めない（他が開いている等） | 学習なしで起動し、10 秒後に 1 回だけ読み直す | 読み直しても駄目なら、あり |
| 辞書キャッシュが読めない | 消して、辞書から 1 回だけ作り直す（数分。その間 `progress` を出す） | 起動中の表示（§9.2） |
| 辞書ファイルが無い・ハッシュが違う | **止まる**（終了コード 21） | あり |
| LM のモデル・torch が読めない | LM なしで起動（変換はできる） | あり |
| Python のモジュールが読めない | **止まる**（終了コード 20） | あり |

辞書の読み込みから、黙って飛ばす処理（`_parse_dict_files` の `continue`）を削る。辞書は照合済みなので、
形式がおかしければ止まるのが正しい。

辞書キャッシュは、**辞書マニフェストのハッシュを名前にして**、一時ファイルに書いてから置き換える。
「古い辞書のキャッシュを使ってしまう」「書きかけが残る」が、起こりえなくなる。

LM は `local_files_only=True` で読む。**エンジンはネットワークに一切つながない。**

### 6.3 準備完了の前に温める

`ready` を出す前に、ダミーの変換を 1 回実行する（実測: 初回 617ms、2 回目以降 9ms）。
利用者の最初の打鍵が遅くならない。

### 6.4 要求 1 件ごとの防壁

エンジンの要求処理ループは、要求 1 件の処理全体を 1 つの `try` で囲む。例外が出たら:

1. `logs\engine.log` に、例外の型と発生箇所（ファイル名・行番号・関数名）を書く。**入力した文字は書かない。**
2. そのセッションを `reset` する。
3. `{"sid":…,"seq":…,"error":true, …リセット後の状態… }` を返す。

エンジンは落ちない。TIP は `error` を見て、見えている文字をそのまま確定する（§7.5）。

これは「握りつぶし」ではない。違いは 3 つ: **記録が残る**、**利用者の文字は残る**、**壊れた状態を捨てて
きれいな状態から続ける**。同じ防壁は 1 か所だけに置き、変換の中身（`session.py` 以下）には置かない。

### 6.5 入力の長さの上限

変換中の入力は `MAX_TOKENS`（200）まで。達したら、文字キーは受け取るが何も変えず、返事に `"full":true`
を付ける。TIP は §9.2 の「長すぎます」を出す。変換時間は長さに比例する（200 字で 38ms）ので、
これで 1 回の要求の所要時間に上限が付く（I-4）。

### 6.6 止まるときは理由を残す

起動できないと判断したら、標準エラーに `fatal <コード> <英数字の短い説明>` を 1 行書いて、決まった終了コードで終わる。
ブローカーはコードを §9.3 の文言に対応させる。

| 終了コード | 意味 |
|---|---|
| 20 | プログラムのファイルが読めない |
| 21 | 辞書ファイルが無い・壊れている |
| 22 | 辞書キャッシュを作り直せなかった（ディスクの空き等） |
| それ以外 | 予期しない終了（OS の終了コードをそのまま記録） |

### 6.7 学習履歴（`learning.py`）の作り直し

いまの問題: 確定のたびに 1 行追記し、直後にファイル全体を読み直す。整理の処理が無い（A-9）。

新しい規則:

1. **自分が書いた分は読み直さない。** 追記したら、同じ行をメモリ上の索引にも足し、
   「ここまで読んだ」位置を進める。確定 1 回のコストは行数によらず一定。
2. **他のプログラム（設定ウィンドウ）が書いた分は、続きだけ読む。** 変換のたびにファイルの大きさを見て、
   覚えている位置より伸びていれば、その差分だけ読んで索引に足す。
   縮んだ・別のファイルに入れ替わった（整理や全消去）ときだけ、全体を読み直す。
3. **整理は起動時に 1 回。** 行数が「生きている記録の 2 倍」かつ `COMPACT_MIN_LINES`（5,000）を超えていたら、
   生きている記録だけを一時ファイルに書き、元のファイルを `learning.jsonl.bak` に回してから置き換える。
   「生きている」とは: 取り消し・抑制されておらず、同じ（読み・表記・左文脈）の中で最新のもの。
   加えて、最後の確定から `LEARN_EXPIRE_DAYS`（365 日）を過ぎた記録は落とす——半減期 30 日なので、
   重みは 0.02% 未満で変換結果に影響しない。ただし利用者が教えた未知語（`user_word`）は期限で落とさない。
4. **書けなかったら**（ディスクの空きが無い等）、メモリ上の索引には反映したまま続け、
   注意を 1 回出す（§9.3）。変換は止めない。
5. 行ごとの細かい型検査は、「JSON として読めて、必要な項目がある」だけに減らす。

合格条件: 10 万行の履歴で、確定 1 回の追加時間が 5ms 以下。起動時の整理後、行数が生きている記録数と一致。
整理の途中でプロセスを殺しても、元のファイルか新しいファイルのどちらかが完全な形で残る。

学習の入／切は、ファイルの有無ではなく `config.json` の `learning`（`on`／`paused`／`off`）で決める。
ファイルが無ければ作る。既存の `.paused` ファイルがあれば、初回に `paused` として引き継ぐ。

## 7. TIP（`yuragi_tip.cpp`、通信と生存管理を書き直す）

TSF とのやりとり（キーの受け取り、変換中の文字の描画、表示属性、候補ウィンドウ、言語バー、
トグルキー）は、動いているので骨格を残す。**消すものと、入れ替えるものを明確にする。**

### 7.1 消すもの

| 対象 | 理由 |
|---|---|
| `Server::Run` のループ、`SpawnResident`、`ResolvePython`、`FindPython`、`SpawnAdminUi` | TIP は Python を知らない（A-1, A-7） |
| TCP 接続、`endpoint.json` とトークンの読み取り、Winsock | パイプに置き換え |
| `ParseReply` の全項目必須検査、`hello.object.size() != 3` | §5.5 の互換の規則（A-6） |
| `__try / __except` 4 か所 | A-11。試験と単純化で品質を上げる |
| 16ms の常時タイマー | §7.6（A-12） |
| 打鍵ごとの `PasswordScope` 同期問い合わせ | §7.7（A-12） |
| `TraceAltToggle` と関連フラグ、既定での `Log()` | 調査の残骸。ログは `tip.json` の `log:true` のときだけ |
| 「返事が遅い → 接続を切る → 変換中の文字を消す」 | §7.4（A-10） |
| 「アプリが編集を断った → 接続を切る」 | 無関係（A-10） |
| HKCU への COM 登録、`SECUREMODE` の掃除、QPC と `HOMEDRIVE` の代替経路 | 起きない |
| `GUID_TFCAT_TIPCAP_UIELEMENTENABLED` の申告 | 実装していない機能を名乗らない |

### 7.2 接続（`Server` 構造体を `BrokerLink` に置き換える）

- `Tip` 1 個につき、パイプ 1 本と読み取りスレッド 1 本。
- 読み取りスレッドは、届いた 1 行ごとに解析して、TIP のメッセージ専用ウィンドウへ `PostMessage` する。
  それだけ。ループの中で待つのは「パイプの読み取り」「停止の合図」「接続の合図」の 3 つで、**時間で回るものは無い**。
- 接続を試すきっかけは 3 つだけ: `ActivateEx`、かな入力モードで打鍵があったとき、利用者がメニューで
  「もう一度試す」を選んだとき。前回の試みから `CONNECT_MIN_INTERVAL_MS`（2 秒）以内なら試さない。
- 書き込みは UI スレッドから。重ね合わせ I/O で、`KEY_BUDGET_MS` 以内に書けなければその打鍵は素通し。

### 7.3 ブローカーがいないとき（TIP が起動してよい唯一のもの）

パイプが無かったとき、**次の全部が成り立つ場合に限り**、ブローカーを 1 回起動する。

1. `HKCU\Software\yuragi-ime\Tag` が、この DLL のタグ（ビルド時に埋め込む）と同じ。
   ——アンインストール済み・更新済みの古い DLL は、ここで必ず止まる。
2. 保守中の印 `Local\yuragi-ime-maintenance` が無い。——インストーラの作業中は誰も起動しない（A-5）。
3. このプロセスが、サンドボックスの中でなく、管理者権限でもない（整合性レベルが「中」）。
   ——ブローカーが変な権限で動かないように（A-8）。条件に合わないプロセスは**接続するだけ**。
4. このサインインの間に TIP が起動した回数が `BROKER_MAX_SPAWNS`（3）未満。回数は、サインアウトで消える
   場所に置く（`HKCU\Software\yuragi-ime\Session`、揮発キー）【実装時に確認: 揮発キーが消える時点】。
   読み書きはミューテックス `Local\yuragi-ime-spawn` で直列にする。ブローカーは READY が 60 秒続いたら回数を 0 に戻す。

起動のしかた: 実行ファイルは**この DLL と同じフォルダ**の `yuragi-broker.exe`（`Program Files` の中なので
書き換えられない）。フラグは `CREATE_NO_WINDOW | CREATE_BREAKAWAY_FROM_JOB`、ハンドルは引き継がない、
環境は `CreateEnvironmentBlock` で作ったもの。ジョブからの離脱が許されず起動に失敗したら、**やり直さない**
（回数だけ数える。別のアプリの TIP が次の機会に試す）。

起動したら、パイプが現れるのを最大 `BROKER_WAIT_MS`（10 秒）待つ（100ms 間隔。上限のある待ち）。

通常はサインイン時に Run キーでブローカーが起動しているので、この経路は「ブローカーが何かで消えた」
ときの回復用である。

### 7.4 打鍵の処理（P-1 と I-4 の中心）

1. `OnTestKeyDown`: 現行どおり、手元の状態だけで「食べるか」を答える（通信しない）。
   ただし**返事を待っている要求が 1 件でもあれば、「変換中」とみなして**判定する
   ——待っている文字キーが届けば変換中になるので、後から来た Enter や BS が先にアプリへ抜けるのを防ぐ。
2. `OnKeyDown`: 要求に通し番号 `seq` を付けて送り、その番号の返事を最大 `KEY_BUDGET_MS`（200ms）待つ。
   - **間に合った** → 現行どおり、同期の編集セッションで画面に反映し、返事に従って食べる／通す。
   - **間に合わなかった** → 1 の判定どおりに食べて、すぐ戻る。**接続は切らない。画面も触らない。**
     返事は後で読み取りスレッドから届く。届いたら非同期の編集セッションで反映する。
3. 返事は必ず `seq` の順に反映する。前の返事がまだなら、届いても待たせる（読み取りは 1 本なので
   順番どおりに届く。UI スレッド側で同期待ちと非同期到着が交差する場合だけ注意）。
4. 待っている要求が `PENDING_NOTICE_MS`（1 秒）を超えたら、§9.2 の「準備しています…」を出す。返事が来たら消す。

つまり TIP にとって、エンジンの一時的な遅れも、落ちて起動し直している最中も、**同じ「返事が遅い」**である。
特別な回復処理は TIP に無い。

### 7.5 「見えている文字をそのまま確定する」

次のどれかを受け取ったら、変換中の文字列があれば**その表示のまま確定して**（文字は消さない。
変換を終了するだけ）、手元の状態を初期化する。

- `{"event":"reset"}`（エンジンが入れ替わった）
- 返事の `"error":true`（その要求で例外が出た）
- 返事・通知の `state` が `down` `maintenance` `incompatible` `not-installed`
- パイプが切れた（ブローカーが消えた）

現行の `ClearLocal()` は文字を消す（`Discard`）。これを「確定して終わる」に変える。文字を消してよいのは、
利用者が Esc を押したときと、フォーカスが移ってアプリが変換を打ち切ったときだけ。

### 7.6 タイマー

- 常時タイマーは持たない。返事の `timer`（同時打鍵の判定期限、LM 待ちの次の問い合わせ時刻）があるときだけ、
  その時刻に 1 回鳴るタイマーを掛ける。鳴ったら `timeout` を送る。
- 候補ウィンドウの位置は、TSF の配置変更通知（`ITfTextLayoutSink::OnLayoutChange`）で直す。
- トグルキーを離したことの確認（予約キーは離した通知が来ないことがある）は、次の打鍵のときに
  `GetKeyState` で見る。

### 7.7 パスワード欄

入力欄の種類は、**フォーカスが移ったときに 1 回**調べて覚える（読み取り専用の編集セッション）。
同期で調べられなければ非同期で頼み、答えが出るまでは「調べ中」として素通しにする。
「選択範囲が取れない」「入力欄の種類が取れない」は、パスワード欄の証拠として扱わない。
打鍵ごとの問い合わせはしない。

### 7.8 試験

TIP 本体は TSF の中でしか動かないが、**判断の部分は切り出して普通の試験にできる**。

- 「返事の解釈」「食べるかどうかの判定」「seq の順序付け」「状態から表示への対応」を、TSF に依存しない
  ヘッダ（`src/tip/tip_logic.h`）に出し、`tip_json_test` と同じ形で試験する。
- 全体は §10 の実地試験（Windows サンドボックス）で確かめる。

## 8. インストール・更新・アンインストール

### 8.1 共通の仕組み

- **保守中の印**: `setup.ps1` と `uninstall.ps1` は、最初に（管理者権限でない側で）ミューテックス
  `Local\yuragi-ime-maintenance` を作って持つ。スクリプトが終われば、成功でも失敗でも強制終了でも、
  Windows が自動で消す。**消し忘れが起こりえない。** この印がある間、TIP はブローカーを起動せず、
  ブローカーはエンジンを起動しない。
- **管理者権限で行うのは 3 つだけ**（UAC は 1 回）: ①`Program Files` への 2 ファイルの配置、
  ②`regsvr32` による登録／解除、③古い版の `Program Files` 側の削除。
  これは小さな PowerShell スクリプト（`packaging/elevated.ps1`）にまとめ、**Python は管理者権限で動かさない。**
  配置する 2 ファイルは、ハッシュを引数で受け取って照合してから置く。
  結果は終了コードと、利用者側が読める結果ファイルで返す。
- **登録の確認**: 登録／解除のあと、レジストリを読み返して確かめる。確かめられなければ失敗として扱う（I-6）。
  `register_admin.py` `unregister_admin.py` は削除する。`DllUnregisterServer` は失敗を返すようにする。
- **言語一覧への追加・削除**（`InstallLayoutOrTip`）は利用者ごとの設定なので、管理者権限でない側で行う
  （別の管理者アカウントで昇格したとき、その管理者の設定を変えてしまわないように）。
- 事前の接続確認（6 か所への TCP 接続）、Python の探索、venv 経路、`-EmbeddedPython`、
  「開発用なので照合なし」の分岐は削除する。

### 8.2 インストールと更新（同じ手順）

| 段 | すること | ここで失敗したら |
|---|---|---|
| 1 | 保守中の印を立てる | — |
| 2 | `staging\<tag>\` に取得・照合・展開。足りない共有物（ランタイム・辞書・モデル）だけ `shared\` に作る。共有物は「作りかけの名前で作って、完成したら改名」 | 何も変わっていない。旧版が動き続ける。やり直せば続きから |
| 3 | **本物のブローカーで試運転**: `yuragi-broker.exe --selftest <staging の engine.json>`。エンジンを実際に起動し、変換を 1 回行い、ウィンドウが出ないことを確かめて終了コードを返す | 同上 |
| 4 | `staging\<tag>` を `versions\<tag>` へ改名（一瞬） | 同上 |
| 5 | 管理者権限: `Program Files\yuragi-ime\<tag>\` に配置、登録を新しい DLL に付け替え、読み返して確認 | 旧版の登録のまま。旧版が動き続ける |
| 6 | 旧ブローカーに `quit`。`HKCU\…\Tag` と Run キーを新しい版に書き換え、言語一覧に追加 | — |
| 7 | 新ブローカーを起動し、`ready` を待って確認（最大 60 秒）。印を下ろす | 理由を表示。次のサインインでも起動を試みる |
| 8 | 旧版の片付け: `versions\` と `shared\` の使われていないもの。`Program Files` 側の旧版は 5 の管理者権限の中で消し、使用中の DLL は「次の Windows 起動時に削除」に予約 | 片付けの失敗はインストールの失敗にしない。次回の setup がまた試す |

- 4 までは、動いている版に一切触らない。5〜7 は数秒。
- 更新のあと、開いたままのアプリには旧 DLL が残る。旧 DLL は §7.3 の条件 1 により何も起動せず、
  新ブローカーに接続する（プロトコルが同じなら、そのまま動く。違えば §9.2 の案内）。
- 初回の途中失敗（A-16）: `staging\` は自分の作業場なので、いつでも消して作り直してよい。
  「未知の内容があります」で止まる検査は削除する。

### 8.3 アンインストール

1. 保守中の印。
2. `HKCU\…\Tag` と Run キーを消す（**最初に。**これで残った DLL は何も起動しなくなる）。言語一覧から外す。
3. ブローカーに `quit`（エンジンも終了する）。
4. 管理者権限: 登録解除、読み返して確認。`Program Files\yuragi-ime\` を削除。使用中の DLL は
   「次の Windows 起動時に削除」に予約。
5. `%LOCALAPPDATA%\yuragi-ime\` を削除（ここには、もう使用中のファイルは無い）。
6. 結果を表示する。使用中の DLL が残ったときは「アプリを開いたままでも問題ありません。
   残り 1 ファイルは、次に Windows を起動したとき自動で消えます」と伝える。**サインアウトや再起動を求めない。**

`~\.yuragi-ime\`（学習履歴・個人辞書・設定）は**残す**。消すのは `-RemoveData` を付けたときだけで、
そのときも消す前に場所と大きさを表示する（I-7）。`-KeepData` は廃止。

### 8.4 開発時（`dev-build.ps1`）

- ビルドと登録を分ける: `dev-build.ps1`（ビルドとテストだけ。CI もこれ）と `dev-register.ps1`（登録）。

## 9. 利用者に見えるもの

原則: **普通の利用者は、「ゆ」と「Y」以外のものを見ない。** 見せるのは、利用者が何かしないと
直らないときだけ。見せるときは、何が起きたか・文字は無事か・どうすればよいか、を 1 つの文で言う。
どれも**フォーカスを取らず、クリックしなくても消える。**

### 9.1 状態は 4 つ

| 状態 | タスクバー | 打鍵 | いつ |
|---|---|---|---|
| 通常 | 「ゆ」／「Y」 | 変換される | ほぼ常に |
| 準備中 | 「ゆ」（薄く） | 預かって、準備ができたら順に入る | サインイン直後の数秒、エンジンの起動し直し中 |
| 停止 | 「!」 | そのまま通る（直接入力と同じ） | 自動で直せなかったとき |
| 対象外 | 「Y」 | そのまま通る | 更新作業中、この利用者には未インストール、アプリの開き直し待ち |

### 9.2 カーソルの近くに出す小さな表示

候補ウィンドウと同じ作り（`WS_EX_NOACTIVATE`。フォーカスを取らない・クリックを取らない）で、
文字入力位置の下に 1 行だけ出す。

| いつ | 文言 | 消える条件 |
|---|---|---|
| 返事を 1 秒以上待っている | `変換の準備をしています…` | 返事が来たら |
| 停止中に、かな入力のつもりで文字キーを押した（フォーカスごとに 1 回） | `日本語変換が止まっています。タスクバーの「!」を押してください` | 4 秒 |
| 入力が上限に達した | `長すぎます。いったん確定してください` | 次の確定 |
| プロトコルが合わない | `ゆらぎを更新しました。このアプリを開き直すと使えます` | 4 秒（フォーカスごとに 1 回） |

### 9.3 通知（ブローカーが出す。停止に入ったときに 1 回だけ）

Windows の通知（`Shell_NotifyIcon` の通知。フォーカスを取らない【実装時に確認】）で:

> **ゆらぎ: 日本語変換が止まりました**
> 入力済みの文字はそのまま残っています。ここを押すと、原因と直し方を表示します。

押すと、ブローカーが小さな案内（ネイティブのダイアログ。Python に頼らない——Python が壊れているときにも
出せるように）を開く。これは利用者が押して開くものなので、ウィンドウを出してよい。

| 原因（終了コード等） | 案内の本文 | ボタン |
|---|---|---|
| 20, 21 | 必要なファイルが見つからないか、壊れています。入れ直すと直ります。学習した内容と登録した単語は残ります。 | `入れ直す手順を開く` `閉じる` |
| 22 | 辞書の準備ができませんでした。ディスクの空きを確認してください（約 300MB 必要です）。 | `もう一度試す` `閉じる` |
| 繰り返し落ちた | 変換プログラムが繰り返し止まりました。 | `もう一度試す` `記録のフォルダを開く` `閉じる` |
| 反応しなくなった | 変換プログラムが反応しなくなりました。 | 同上 |

停止していても起動はできている軽い異常（設定ファイルが読めず既定値で動いている、LM が使えない、
学習を保存できない）は、「注意」として同じ通知の仕組みで**原因ごとに 1 サインイン 1 回**:

> **ゆらぎ: 設定ファイルを読めませんでした**
> 標準の設定で動いています。変換は使えます。ここを押すと詳しく表示します。

### 9.4 タスクバーのメニュー（右クリック）

| 状態 | 項目 |
|---|---|
| 通常 | `直接入力に切り替え`／`かな入力に切り替え`、`設定を開く` |
| 準備中 | `（変換の準備をしています）`（押せない）、`設定を開く` |
| 停止 | `もう一度試す`、`原因を表示`、`設定を開く` |

設定ウィンドウは TIP が起動するのではなく、ブローカーに `open_admin` を頼む（ブローカーが `pythonw.exe` で起動）。
設定ウィンドウの「状態」タブに、ブローカーとエンジンの状態・注意・最後に止まった理由・学習履歴の行数を出す。
設定を変えたあとの「変換エンジンを再起動」は、ブローカーへの `retry` と同じ仕組みで行う
（いまは「止めれば TIP が起動し直す」ことに頼っている。その前提は無くなる）。

## 12. 今回やらないこと（理由つき）

| 項目 | 理由と、やる場合の方向 |
|---|---|
| **辞書のメモリ（1,260MB）と読み込み時間（2.35 秒）の削減** | この設計で残る最大の弱点。メモリが足りない PC では、エンジンが OS に止められやすい。辞書を Python のオブジェクトとして持つのをやめ、ファイルを直接参照できる形式にすれば、メモリも起動時間も 1 桁下がる見込み。変換の中身に触るので、今回の作業（構造の作り直し）とは分けて、次に行う |
| LM を別プロセスに分ける | torch が原因でエンジンごと落ちる事例が `engine.log` に出たら行う。分け方は「候補の生成はエンジン、点数付けだけ LM プロセス」。いまは事例が無いので作らない |
| 32 ビットアプリ、ARM 版 Windows | 配置と通信は対応できる形にしてある（パイプはビット数に依らない）。DLL を追加でビルドすれば足りる。まずは setup で ARM を「非対応」と表示して止める |
| 打鍵の記録・再生による変換状態の完全復元 | §2.3。状態が増える割に、得るものが小さい |
| 自動更新 | 利用者が頼んでいないときに何かを取りに行かない |

## 13. 実装時に確認すること

- パイプのアクセス権: サンドボックス内のアプリ（スタートメニューの検索欄）から接続できる設定。
  できない場合、そこでは「対象外」として素通しにする（何も起動しないことは §7.3 で保証済み）。
- `CREATE_BREAKAWAY_FROM_JOB` が拒否される環境での挙動（拒否されたら起動しない、でよいことの確認）。
- 揮発レジストリキーが消える時点（サインアウトで消えること）。消えないなら、ブローカーのミューテックスが
  無いことを「新しいサインイン」の印にする。
- `Shell_NotifyIcon` の通知が、全画面アプリの上でフォーカスを取らないこと。
- 「次の Windows 起動時に削除」の予約（`MoveFileEx`）が、`Program Files` 内のファイルとフォルダで働くこと。
- 候補ウィンドウの位置直しを配置変更通知に替えたとき、通知を出さないアプリが無いか
  （あれば、候補を表示している間だけ 100ms のタイマーを使う）。
